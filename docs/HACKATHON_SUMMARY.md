## 2. Веса критериев оценки онлайн-этапа

Итоговый балл складывается из двух частей:
- **Техническая оценка — 60%**
- **Продуктовая оценка — 40%**
- **Платформенный бонус — +0.15 балла** (начисляется целиком за расширенное использование фичей платформы MAX сверх обязательного минимума).

### 2.1. Техническая оценка (60%)
| Критерий | Доля | На что смотрят эксперты |
|---|---|---|
| **Работоспособность и полнота функций** | 30% | Основной сценарий проходится от начала до конца без сбоев. |
| **Корректность интеграции и данных** | 20% | Предсказуемый обмен данными, внешние интеграции работают по заявленной логике. |
| **Техническая реализация и архитектура** | 20% | Чистая архитектура, разделение слоев, готовность к поддержке и развитию. |
| **Стабильность и обработка ошибок** | 10% | Устойчивость к некорректному вводу, пользователь может продолжить без перезапуска, отсутствие таймаутов. |
| **Безопасность и зависимости** | 10% | **Никаких секретов/токенов в коде**, версии библиотек зафиксированы, безопасная работа с данными. |
| **Техническая документация** | 10% | Воспроизводимый запуск по README, описание архитектуры, тестовые данные, ограничения. |

### 2.2. Продуктовая оценка (40%)
| Критерий | Доля | На что смотрят эксперты |
|---|---|---|
| **Потенциал масштабирования** | 35% | Четкое понимание ядра и переменной части (что меняется при тиражировании на другие кампусы / города / активности). |
| **Пользовательская ценность** | 25% | Решение конкретной «боли», подтверждение актуальности, измеримый результат для пользователя. |
| **UX/UI и удобство** | 20% | Понятная навигация, отсутствие тупиков, обратная связь (загрузка, успех, понятные ошибки). |
| **Обоснованность и целостность** | 15% | Логическая связь: проблема → инструмент → результат. Реалистичность ограничений MVP. |
| **Качество презентации** | 5% | Ясность, читаемость схем, отсутствие перегруженных слайдов. |

## 3. Обязательные требования к сдаче (Checklist)

1. **Работающее решение в MAX**:
   - Чат-бот (или чат-бот + мини-приложение), доступный экспертам в течение всего периода проверки.
   - Проверка своего бота: `GET https://platform-api2.max.ru/me` с заголовком `Authorization: <BOT_TOKEN>` возвращает username бота.
   - Документация MAX API: [dev.max.ru/docs](https://dev.max.ru/docs).
2. **Зафиксированная версия кода**:
   - Git-репозиторий (с указанием commit hash) или архив с контрольной суммой.
3. **README.md** со строго обязательными разделами (см. шаблон в корне).
4. **Файл зависимостей**: зафиксированные версии (`requirements.txt`, `poetry.lock`, `package-lock.json` и т.д.).
5. **Docker-конфигурация**:
   - `compose.yaml` или `docker-compose.yml` (запуск всех локальных компонентов **одной командой**).
   - `Dockerfile` для каждого сервиса.
   - `.dockerignore`.
   - `.env.example` без боевых секретов.
   - Сборка должна занимать **не более 5 минут**.
6. **Презентация PDF**:
   - Слайд 1: техническая информация (ссылка на бота в MAX, ссылка на git + коммит, рабочие токены/доступы для жюри, краткий порядок сценария проверки).
   - Слайды 2+: продуктовая презентация (проблема, ЦА, To-Be, архитектура, масштабирование).

## 4. Концепция проекта «В сборе»

- **Суть**: сервис быстрой координации и сбора людей для любительского спорта и активностей (волейбол, футбол, велопрогулки, пробежки).
- **Фокус MVP**: доведение встречи до минимального кворума участников (подтверждение встречи при сборе N человек, автоуведомления, лист ожидания при отменах).
- **Пилотный сегмент**: студенческий кампус / университетское сообщество.
- **Масштабирование**: Кампус → Несколько вузов города → Районные спортплощадки → Другие виды совместного досуга (настолки, волонтерство, мастер-классы).
